# Spec：FumiGit v0.1 — 提交图谱最小闭环

## Problem Statement

开发者日常的 Git 操作在命令行和图形客户端之间来回切换。现有图形客户端要么臃肿迟缓、要么审美过时，而理解一个仓库最重要的视图——提交历史与分支拓扑——在它们里往往只是附带功能。Windows 上缺少一个以提交图谱为核心操作面、视觉专业克制、行为与真 Git 完全一致的轻量客户端。

## Solution

FumiGit v0.1：一个 Windows 桌面 Git 客户端（Tauri），**提交图谱是主角**。

用户把本地仓库加入 FumiGit，看到一张可交互的全分支提交图谱；点选任意提交即刻在右侧看到完整信息与 diff；右侧下方常驻工作区面板完成暂存与提交；顶部动作栏完成与远程的同步。深浅主题跟随系统，行为永远与用户机器上的真 Git 一致（因为后端就是真 Git）。

## User Stories

**仓库管理**

1. 作为开发者，我想通过系统目录选择器把本地文件夹添加为受管仓库，以便开始查看它的历史。
2. 作为开发者，我想看到最近打开的仓库列表并一键切换，以便不必每次重新浏览路径。
3. 作为开发者，当所选文件夹不是 git 仓库时，我想看到明确的引导提示而非空白或报错，以便知道该先初始化还是换目录。
4. 作为开发者，首次启动时我想看到引导页说明如何添加第一个仓库，以便不迷路。

**提交图谱**

5. 作为开发者，我想看到覆盖全部分支的提交图谱（分支线、分叉点、合并点用彩色曲线绘制），以便一眼理解仓库的拓扑历史。
6. 作为开发者，我想在图谱每一行看到提交信息、ref 徽章（本地分支/远程分支/HEAD/标签）、作者、相对时间与短 hash，以便快速定位与识别提交。
7. 作为开发者，我想点击图谱中任意提交并看到它被选中（高亮 + 右侧联动），以便从容地浏览历史。
8. 作为开发者，我想用键盘上下键在提交之间移动、回车聚焦详情，以便不离开键盘完成浏览。
9. 作为开发者，我想在十万级提交的仓库上以 60fps 滚动图谱，以便它在大仓库上依然可用。
10. 作为开发者，我想用工具栏刷新按钮看到仓库的最新状态，以便图谱反映真实当前历史。
11. 作为开发者，我想按提交信息或作者做子串过滤，以便在漫长历史里快速找到目标提交。
12. 作为开发者，我想看到当前分支相对远程领先/落后的提交数（↑↓），以便知道是否需要推送或拉取。

**提交详情与 diff**

13. 作为开发者，我想看到选中提交的完整信息、作者、时间、父提交与所属 ref，以便理解该提交的上下文。
14. 作为开发者，我想看到该提交变更的文件列表与每个文件的增删行数统计，以便快速评估变更范围。
15. 作为开发者，我想看到逐行 diff（行号 + 增删着色 + 等宽字体），以便审查代码变更。
16. 作为开发者，对合并提交我想看到其父提交引用（无直接 diff），以便理解合并来源。

**工作区、暂存与提交**

17. 作为开发者，我想在工作区面板看到已暂存/未暂存文件列表（M/A/D 状态标记），以便掌握当前所有改动。
18. 作为开发者，我想暂存与取消暂存单个文件，以便精确控制每次提交的内容。
19. 作为开发者，我想输入提交信息并把已暂存改动提交到当前分支，以便保存进度。
20. 作为开发者，当提交信息为空时我想被阻止并提示，以便避免产生空信息提交。

**远程同步**

21. 作为开发者，我想一键 fetch 只更新远程跟踪分支而不改动工作区，以便先观察远程动向。
22. 作为开发者，我想 pull 以快进方式更新当前分支，以便与远程保持同步。
23. 作为开发者，当 pull 无法快进（历史分叉）时，我想看到明确的失败说明而非静默合并，以便自己决定如何处理。
24. 作为开发者，我想 push 当前分支到其上游，以便共享我的提交。
25. 作为开发者，当 push 被拒绝（非快进）时，我想看到明确错误与下一步建议，以便知道该先拉取。
26. 作为开发者，我想看到每个远程操作的进行中/成功/失败状态反馈，以便了解操作结果而不是面对无响应的按钮。
27. 作为开发者，push/pull 私有仓库时我想复用系统已配置的凭证（credential helper、SSH agent），以便不需要在客户端里重复配置账号。

**外观与体验**

28. 作为开发者，我想在深色/浅色/跟随系统三种主题间切换且选择被记住，以便匹配我的使用环境。
29. 作为开发者，我希望窗口最小尺寸下三栏布局依然可用，以便小屏不被挤压变形。

## Implementation Decisions

以下均为本项目已通过盘问/原型确定的决策（背景：AGENTS.md、docs/design/ui-spec.md）：

- **技术栈**：Tauri 2（Rust 后端 + WebView 前端）；前端 React 19 + TypeScript + Tailwind v4 + Zustand + TanStack Virtual；Rust crate 与前端通过 Tauri IPC 通信。
- **Git 接入（ADR 级决策）**：git CLI 是唯一 Git 后端。Rust 侧 spawn git 进程并解析 `--porcelain`/`--format` 输出；不引入 libgit2/gitoxide 作为行为来源。由此免费继承用户的 gitconfig、hooks、credential helper 与 SSH agent。频繁调用通过常驻/复用进程池优化。
- **IPC 命令集（前后端契约）**：`open_repo`、`list_recent_repos`、`add_recent_repo`、`get_log`（增量分页）、`get_status`、`stage`、`unstage`、`commit`、`fetch`、`pull`、`push`、`get_branch_summary`。TS 侧类型与 Rust serde 结构镜像，前端只允许通过类型化封装调用，禁止裸字符串命令。
- **布局**：定稿为三栏工作台（侧栏 216px / 图谱自适应 / 详情+工作区 396px），窗口 1280×800、最小 960×640。度量与配色以 docs/design/ui-spec.md 为唯一来源。
- **主题**：深/浅/跟随系统三态，CSS 变量驱动，`data-mode` 由前端 store 管理；选择持久化到本地配置。
- **图谱渲染**：Canvas 2D + 虚拟滚动（行高 52px、lane 步进 15px、图列宽 96px）。lane 分配规则源自已归档原型：按时间倒序遍历提交，first parent 延续当前 lane，其余 parent 各生成新 lane（从 8 色分支调色板取下一色），空 lane 立即回收压缩；HEAD 节点加大并描边。
- **最近仓库持久化**：本地 JSON 配置文件（应用配置目录），不引入数据库。
- **搜索**：对已加载提交按信息/作者做子串过滤，不建索引、不搜索文件内容。
- **pull 策略**：`--ff-only`；失败时返回结构化错误，由前端展示指引，v0.1 不做合并界面。
- **刷新机制**：监听 `.git` 目录文件事件 + 工具栏手动刷新；不自动 fetch。
- **平台中立**：路径拼接、配置目录、换行处理全部走抽象，不写死 Windows 假设。

## Testing Decisions

- **好测试只测外部行为**：断言"给定真实仓库状态，接口返回这样的结构化结果"，不测内部函数如何拆分、不测实现细节。
- **主接缝（唯一承重接缝）：Rust 侧 git 命令封装层。** 测试用真实 git 在临时目录构造夹具仓库，断言封装层对外的结构化输出与命令结果。夹具矩阵：空仓库、单分支线性历史、多分支合并拓扑、分离 HEAD、含标签、中文路径、非仓库目录、十万级提交（性能基准）。不 mock git 本身——解析逻辑对真 git 的真实输出负责。
- **次接缝（前端，轻量）**：图谱 lane 分配算法作为纯函数直接测（输入提交列表，断言 lane/颜色/边）；前端 store 以打桩 IPC 返回夹具数据测试状态流转。不为组件写 Testing Library 交互测试。
- **先例**：绿地项目无既有测试；本 spec 的测试将确立仓库约定——夹具构造器作为共享测试工具放在 Rust 测试模块内。
- 不建浏览器 E2E；MVP 阶段 UI 靠手动验证。

## Out of Scope

- 分支管理 UI：新建/删除/切换/合并/rebase/cherry-pick（切换分支仅通过… 无，v0.1 完全不含分支写操作）
- 可视化冲突解决、hunk 级部分暂存、stash
- 丢弃/checkout 单文件改动
- AI 能力（提交信息生成、diff 解释、冲突辅助）
- macOS / Linux 发布、自动更新、安装包代码签名
- "仓库地图"横向第二视图（原型变体 C，远期备选）
- 凭证管理界面（完全依赖 git 自身凭证体系）
- 提交内容全文搜索、文件历史 Blame 视图

## Further Notes

- 设计定稿与截图：`docs/design/ui-spec.md`、`docs/design/variant-a-{dark,light}.png`。
